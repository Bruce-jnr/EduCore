# Google school registration

New Google users explicitly create a new BASIC school with a trial School Administrator account. No existing password account is linked by email. A globally unique Google subject permits one school registration per Google account, including deleted accounts. Existing password users continue to use their current sign-in. Account linking and joining existing schools are outside this feature.

## Activation
1. Back up and review pending Prisma migrations, including the earlier lesson-plan migration. Apply reviewed migrations in your deployment process; none were run during implementation. The Google migration adds nullable `User.googleSubject` and a unique index. Existing users retain null. MySQL DDL may lock the User table; plan deployment accordingly. Rollback requires removing the index/column and loses Google identity links.
2. Regenerate Prisma Client with `npm run prisma:generate` before restarting the API. Stop your own running API first if Windows locks its Prisma engine. Deploy schema and generated client before enabling the new API.
3. Create a Google OAuth client of type Web application. Add the actual frontend origin (for example http://localhost:5173) to Authorized JavaScript origins and configure branding, consent, authorized domains and test users as required. This uses the GIS JavaScript popup callback, not an OAuth redirect endpoint. No Google client secret is used.
4. Set `GOOGLE_CLIENT_ID` in the server environment; set `CLIENT_URL` to the exact frontend origin and restart the API. No secrets belong in frontend variables. The public client ID is returned by `/api/auth/google/config`.
5. Ensure normal tenant permissions have been seeded, then enable existing Platform Settings → registration. Registration remains closed when that flag is false, settings are missing, or maintenance mode is active. Trial duration, country, currency and timezone come from platform settings. Seed execution and database changes require operator review; do not rerun seed blindly.

## Security and transaction behavior
Google Auth Library verifies the token signature, audience, issuer and expiry. The server additionally requires a verified email and a matching signed, five-minute intent-bound nonce. Challenges use a dedicated HMAC format, never application JWTs. Callback requests must be JSON with an Origin exactly matching CLIENT_URL; this is the JavaScript callback flow, not Google's direct credential POST/double-submit-cookie flow. No Google tokens or credentials are stored or audited. Google identity is keyed by `sub`, never by email; third-party Google email addresses are not authoritative proof for linking or recovering existing accounts.

Identity verification and password hashing occur before the transaction. New tenant, settings, administrator role, user, login timestamp and audit entry commit together. A random, undisclosed password preserves compatibility with the required passwordHash column. Any future password reset must require independent verified ownership. Google sign-in checks user/tenant status and subscription, and commits login metadata and audit together. Audit failure rolls the operation back. Unique subject, tenant slug and school code constraints roll back concurrent duplicate registrations; a conflict returns HTTP 409. This is duplicate prevention, not request replay returning the original response: if the response is lost, use Google sign-in. Session signing follows commit.

The API includes a bounded per-process IP rate limiter (30 Google POSTs per ten minutes, including challenges). Multi-instance deployments require a shared or edge limiter. Configure trusted proxies carefully before relying on forwarded client IPs. Serve production frontend over HTTPS. Its CSP must permit Google's documented GIS script/frame/connect endpoints; popup fallback may need Cross-Origin-Opener-Policy: same-origin-allow-popups on the frontend response. API CORS already uses CLIENT_URL. A production browser test must verify hosting headers, Google consent and real tokens.
